# Feasibility milestone status

Date: October 17, 2026. Encrypted storage and service foundations are implemented in a local Git project, and a synthetic-only editor preview (WPF/WebView2 host plus offline Monaco) runs locally. The editor is not connected to the vault, key service or builder. This is not yet a functioning encrypted editor or deployed vault service.

Coordinator ran `scripts/Verify.ps1` against all fifteen projects in Release using Microsoft .NET SDK 10.0.402: **308 .NET checks and 28 editor web tests passed**. Five link tests explicitly skipped because the host could not create symbolic links. Service/storage projects use BCL only. The editor host restores the pinned WebView2 package from the repository-local feed (`vendor/packages`); no remote NuGet source is configured. Monaco is vendored under `src/SourceVault.Editor.Web/vendor/monaco`. Both packages were fetched from their official registries with SHA-512 recorded in `docs/editor-dependencies.json`. `dotnet nuget verify --all` accepted the WebView2 package's Microsoft author signature and NuGet.org countersignature (details in the manifest); the author certificate expires 2026-10-17, inside which the signature was timestamped. The WPF/WebView2 CSP now allows `data:` fonts because Monaco 0.57 inlines its codicon font. The SDK was downloaded into the chat workspace's `work/toolchain/`, verified with SHA-512 against Microsoft's release metadata, and was not installed system-wide. See `toolchain.json` for the recorded package metadata.

Direct DLL execution outside the restricted sandbox was required for IPC verification. An independent native diagnostic established that this environment requires `FILE_READ_ATTRIBUTES` in the pipe ACE; final mask `0x00100083` still excludes `FILE_CREATE_PIPE_INSTANCE`. Restricted-token failures were not treated as successful isolation tests. These results do not establish deployed cross-account access control.

Independent worker reviews checked protocol parsing/framing and native IPC. The latter found a wall-clock expiry issue; it was corrected using monotonic time, terminal invalidation, and simulated-time tests before final verification. These reviews are development checks, not an external security audit.

Read-only provider metadata query succeeded. An earlier `Get-Tpm` result of "no TPM" was wrong: `Get-Tpm` requires administrator rights and was run unelevated. On 2026-10-17, unelevated `tpmtool getdeviceinformation` reported an Intel firmware TPM 2.0 that is present, initialized, ready for storage and not locked out, and the probe reported Platform Crypto Provider hardware. With owner approval, a lab key `SourceVault.Lab.T01` was then created under the interactive user. The private key cannot be exported, and 20 of 20 synthetic wrap/unwrap roundtrips passed, at about 47 ms per TPM unwrap. The spike's decrypt-only policy check refused the key because PCP created a generic sign+encrypt key (`PCP_KEY_USAGE_POLICY = 0x10003`). With creation changed to set `PCP_KEY_USAGE_POLICY` to encryption-only, a second key `SourceVault.Lab.T02` was created decrypt-only and passed `lab-create`, `lab-open` and `lab-roundtrip` (0x10002, export refused, 20/20 roundtrips). Service-identity, reboot and cross-machine gates remain open. See `spikes/tpm/EVIDENCE.md`. Hyper-V and Docker tooling were unavailable. No WSL instance was started. Windows services, persistent TPM keys, machine ACLs, VM configuration, or security policies were not provisioned. Initial SDK bootstrap emitted a development-certificate installation message before certificate generation was disabled; no certificate-trust operation was requested. The verifier disables certificate generation and redirects tooling state into the workspace.

The Linux wrapper passed `bash -n` syntax validation using Git Bash outside the sandbox; Linux runtime behavior remains untested. Test fixture archives deliberately contain synthetic plaintext and are development evidence, not proof of protected source storage.

New storage integration fixtures use ephemeral software RSA confined to test assemblies. The production library has no software protector and the production service cannot select one. Synthetic document content and names were absent from the tested store files; this limited canary scan is not proof of universal non-persistence. The revision suite also exercised a real child-process exclusive lock and four commit interruption stages. Exception fault injection does not establish power-loss durability.

Workers reviewed the binary record layout, codec and revision integrity paths. Review prompted hardening of dangling-link attribute checks. The library still requires an externally provisioned trusted service-owned root/ancestors; it does not establish ownership or prevent a hostile filesystem writer racing operations. Before source endpoints can be enabled, deployment must enforce those ACL prerequisites. List/Open currently authenticate every committed document, so actual TPM throughput is another integration gate.

The service host implements SCM entry points and cancellation, but its ready state means only an existing key opened under the required identity. It exposes no document, build or pipe API. Its synchronous key open has no forced cancellation and requires startup/shutdown timing validation on hardware.

An independent check on 2026-10-17, separate from the test suite, encrypted about 52 KB of synthetic source with a unique canary through `RevisionStore`. Searching the store files found no plaintext, logical filename, UTF-16 copy or 16-byte slice of the source. Ciphertext measured 8.00 bits/byte of entropy and did not compress (the plaintext measured 5.1 bits/byte and compressed to 6.5%). Two revisions shared no wrapped key or ciphertext. A flipped ciphertext, tag, header or wrapped-key bit, truncation, swapping in an older revision, and a different key were all rejected, while an untouched copy opened with the correct key. The key was an in-process software RSA fixture, so this verifies the AES-256-GCM envelope format, not TPM key protection.

The editor is not connected to the encrypted store. The editor preview holds synthetic text in renderer memory only; Save creates session-only revisions that disappear on reload or exit. Code review of the host bridge, navigation policy, frontend and loopback server is recorded in [editor preview checks](editor-preview-checks.md); it is a code inspection, not native runtime validation. WebView2 profile directories are retained under the publish output for later persistence inspection. Registry/policy WebView2 overrides, capture behavior, and renderer/OS persistence remain untested.

## Gates still open

- Actual service host/virtual identity, key/vault/service ACLs, hardware key operations, restart/reboot, export denial, and cross-machine binding.
- Real-hardware validation of record/store integration, power-loss durability, throughput, rotation and chosen recovery design.
- Distinct editor identity and mutual pipe behavior, genuine separate-account/remote-client denial, lock/revocation wiring, signer/path policy and process-lifetime races.
- Editor: interactive native checklist, registry/policy debugging overrides, WebView2 profile/cache/crash persistence inspection, explicit capture-exclusion mode, native confirmation that the stricter `PreviewPolicy` still loads all Monaco assets/workers, and connection to the real service protocol.
- Storage root: wiring the validator into service readiness once the service opens a store, and validation of the full real ancestor chain under the deployed service SID.
- Approved real compiler, authenticated guest channel, VM-management delegation, guest lifecycle, artifact publication, and persistence investigation.
- Offline installer/update signing, recovery drills, license selection and independent security review.

See [next assignments](next-tasks.md) before dispatching further implementation. Only synthetic inputs should be used until the appropriate gates pass.
