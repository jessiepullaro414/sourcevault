# Feasibility milestone status

Updated October 18, 2026. The encrypted store, the vault service with protocol v2 on a named pipe, the editor's vault mode, the importer, file operations, history, merge and container builds are implemented. Owner-run lab checks on one machine covered the installed service, key provisioning, vault root, catalog tamper checks, pipe DACL and lab client. The installed editor, importer and builds have not yet been run against the installed service (see [next tasks](next-tasks.md)). This is a development build for synthetic inputs, not a reviewed security product.

On 2026-10-18 `scripts/Verify.ps1` built all 21 projects in Release with Microsoft .NET SDK 10.0.402: **425 .NET checks and 51 editor web tests passed**. Five link tests explicitly skipped because the host could not create symbolic links. Service/storage projects use BCL only. The editor host restores the pinned WebView2 package from the repository-local feed (`vendor/packages`); no remote NuGet source is configured. Monaco is vendored under `src/SourceVault.Editor.Web/vendor/monaco`. Both packages were fetched from their official registries with SHA-512 recorded in `docs/editor-dependencies.json`. `dotnet nuget verify --all` accepted the WebView2 package's Microsoft author signature and NuGet.org countersignature (details in the manifest); the author certificate expires 2026-10-17, inside which the signature was timestamped. The WPF/WebView2 CSP now allows `data:` fonts because Monaco 0.57 inlines its codicon font. The SDK lives in the git-ignored `local/toolchain/dotnet/` (see [local project](local-project.md)); it was downloaded, verified with SHA-512 against Microsoft's release metadata, and was not installed system-wide. See `toolchain.json` for the recorded package metadata.

Direct DLL execution outside the restricted sandbox was required for IPC verification. An independent native diagnostic established that this environment requires `FILE_READ_ATTRIBUTES` in the pipe ACE; final mask `0x00100083` still excludes `FILE_CREATE_PIPE_INSTANCE`. Restricted-token failures were not treated as successful isolation tests. These results do not establish deployed cross-account access control.

Independent worker reviews checked protocol parsing/framing and native IPC. The latter found a wall-clock expiry issue; it was corrected using monotonic time, terminal invalidation, and simulated-time tests before final verification. These reviews are development checks, not an external security audit.

Read-only provider metadata query succeeded. An earlier `Get-Tpm` result of "no TPM" was wrong: `Get-Tpm` requires administrator rights and was run unelevated. On 2026-10-17, unelevated `tpmtool getdeviceinformation` reported an Intel firmware TPM 2.0 that is present, initialized, ready for storage and not locked out, and the probe reported Platform Crypto Provider hardware. With owner approval, a lab key `SourceVault.Lab.T01` was then created under the interactive user. The private key cannot be exported, and 20 of 20 synthetic wrap/unwrap roundtrips passed, at about 47 ms per TPM unwrap. The spike's decrypt-only policy check refused the key because PCP created a generic sign+encrypt key (`PCP_KEY_USAGE_POLICY = 0x10003`). With creation changed to set `PCP_KEY_USAGE_POLICY` to encryption-only, a second key `SourceVault.Lab.T02` was created decrypt-only and passed `lab-create`, `lab-open` and `lab-roundtrip` (0x10002, export refused, 20/20 roundtrips). Service-identity, reboot and cross-machine gates remain open. See `spikes/tpm/EVIDENCE.md`. Hyper-V and Docker tooling were unavailable. No WSL instance was started. Development checks provisioned no Windows services, persistent TPM keys, machine ACLs, VM configuration or security policies; the service, key and vault root above were set up only by the owner-run lab scripts, with approval. Initial SDK bootstrap emitted a development-certificate installation message before certificate generation was disabled; no certificate-trust operation was requested. The verifier disables certificate generation and redirects tooling state into the workspace.

The Linux wrapper passed `bash -n` syntax validation using Git Bash outside the sandbox; Linux runtime behavior remains untested. Test fixture archives deliberately contain synthetic plaintext and are development evidence, not proof of protected source storage.

New storage integration fixtures use ephemeral software RSA confined to test assemblies. The production library has no software protector and the production service cannot select one. Synthetic document content and names were absent from the tested store files; this limited canary scan is not proof of universal non-persistence. The revision suite also exercised a real child-process exclusive lock and four commit interruption stages. Exception fault injection does not establish power-loss durability.

Workers reviewed the binary record layout, codec and revision integrity paths. Review prompted hardening of dangling-link attribute checks. The library still requires an externally provisioned trusted service-owned root/ancestors; it does not establish ownership or prevent a hostile filesystem writer racing operations. Deployment enforces those ACL prerequisites through the vault-root gate. The schema 2 manifest cache cut TPM unwraps to 0-1 per List/Open/Commit (measured above at 200 files); throughput at larger project sizes is still unmeasured.

The service host implements SCM entry points and cancellation. Startup opens the existing key under the required identity, checks the vault root, verifies the catalog and every project, and then serves protocol v2 on the pipe. Its synchronous key open has no forced cancellation; startup timing has been measured on this machine, but not after a reboot.

An independent check on 2026-10-17, separate from the test suite, encrypted about 52 KB of synthetic source with a unique canary through `RevisionStore`. Searching the store files found no plaintext, logical filename, UTF-16 copy or 16-byte slice of the source. Ciphertext measured 8.00 bits/byte of entropy and did not compress (the plaintext measured 5.1 bits/byte and compressed to 6.5%). Two revisions shared no wrapped key or ciphertext. A flipped ciphertext, tag, header or wrapped-key bit, truncation, swapping in an older revision, and a different key were all rejected, while an untouched copy opened with the correct key. The key was an in-process software RSA fixture, so this verifies the AES-256-GCM envelope format, not TPM key protection.

The editor has two modes ([editor host](editor-host.md)).

- **`--synthetic-preview`:** holds synthetic text in renderer memory only. Save creates session-only revisions that disappear on reload or exit.
- **`--vault`:** talks to the service through `SourceVault.Client.EditorVaultController`. The host holds the capability and revision ids, the renderer sees text only for open files, capture exclusion is on (best effort), and the WebView2 profile is deleted at exit.

On this machine, with a copy of the installed layout, the window reported display affinity `0x11` and its profile was deleted after a normal close and after a killed run. Vault mode has been reviewed in a browser against a fake host, but has not yet run as the installed editor against the installed service. Code review of the host bridge, navigation policy, frontend and loopback server is recorded in [editor preview checks](editor-preview-checks.md); it is a code inspection, not native runtime validation. Registry/policy WebView2 overrides, capture behavior under real capture tools, and renderer/OS persistence remain untested.

Project deletion and importer source cleanup were added on 2026-10-18 (owner request). Vault projects are deleted with a typed exact-name confirmation through protocol v2 `DeleteProject`, using index tombstones so an interrupted deletion fails neither verification nor startup (index document version 2; version 1 still opens). `SourceVault.Import.exe --delete-source` deletes only imported files still identical to the verified vault copy, after a typed `DELETE`, overwriting each first; `.git`, skipped files and anything behind a link are kept. Both are covered by synthetic in-process tests only. They have not yet run against the installed service, and overwriting is not a secure erase on SSDs.

File operations, history, merge and container builds were added on 2026-10-18 (owner-approved design: docs/files-history-builds-design.md).

- **Files:** rename and move files and folders, delete files (restorable from the deleted list), and rename projects.
- **History:** every save is recorded in per-file encrypted history (manifest schema 3; no record-format change), with a read-only comparison view and restore-as-draft. Schema 2 vaults upgrade on their next commit.
- **Merge:** a three-way line merge resolves save conflicts; the merged save lands only on the revision it was merged with.
- **Builds:** a separate build service, NT SERVICE\SourceVaultBuild (same binary, build-service role), holds Docker access. It runs builds in already-running, named containers configured by an administrator in build.json, publishes checked artifacts to an admin-set host folder, and returns logs that the vault service stores encrypted.
- **Tests:** all of this is tested in process: the store, the protocol over real named pipes, the renderer, and builds against an in-memory container and a fake Docker Engine HTTP server on a named pipe.
- **Not yet run on a real machine:** the installed build service, Docker group membership, real Docker engines (Windows containers: copying into a running Hyper-V-isolated container may be unsupported), and the WSL TLS script.

A hardening wave followed on 2026-10-18 (owner decisions in [hardening-design.md](hardening-design.md)). It is tested in process only; the matching lab checks are in [lab-checklist.md](lab-checklist.md).

- **Pipe client PID reuse:** a client process that has exited, or is newer than the connection, is refused.
- **Client hash pins:** the service accepts the editor and importer only while their installed folders exactly match `install-manifest.sha256`.
- **Durable HEAD:** commits flush the swapped `HEAD`.
- **Monaco assets:** every shipped asset is checked against `PreviewPolicy`.
- **Build output:** files that can reveal source are left out and listed in the log.
- **Decided against:** key rotation (out of scope) and the Hyper-V builder (T03, retired).

## Gates still open

Passed on this machine and no longer open: service identity, key provisioning under it with export refused, vault-root and catalog gates, pipe DACL, and the client executable path check (see the Windows service row).

- Restart/reboot persistence, missing-key and bad-config behavior, and cross-machine binding (a copied vault must not decrypt elsewhere).
- Real-hardware power-loss durability and throughput beyond 200 files. (No recovery and no key rotation, by owner decisions 2026-10-18.)
- Client signer check (waits for a signing decision; today: installed path plus hash pins), genuine separate-account/remote-client denial, and lock/revocation across several editors. The pins and the PID-reuse check still need their lab run.
- Editor: the installed `--vault` smoke checklist against the service, the rest of the interactive native checklist, registry/policy debugging overrides, WebView2 profile/cache/crash persistence inspection, capture exclusion under real capture tools, and native confirmation that Monaco works (every asset now passes the policy in a test).
- Importer, file operations, history and merge on the installed service.
- Builds against real Docker engines (WSL TLS, Windows-container copy), including the dropped-file policy; an owner-approval release step (not built); a real compiler.
- Offline installer/update signing and independent security review. (License: MIT, chosen by the owner 2026-10-18.)
